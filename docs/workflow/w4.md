## Requirements

Status: AGREED 2026-08-16 (source note corrected 2026-08-16, w4-D-14; REQ-5 line cites
corrected 2026-08-17, impl-gate r1 finding 2 — citation-level only)
Source: engagement owner ask, 2026-08-16 (Dr. Maya Okonkwo, COO — Riverbend Community
Health), quoted verbatim below, identifiers redacted per the stage rule. Patient ids in
the HAR (`1042`/`1043`) are seeded patient rows — the seed runs 255 patients, ids
1042–1851 — so the captured cross-patient read is against live seeded charts (w4-D-14).

> Patients keep calling to ask how to see their own labs and visit summaries — right now
> it's all scattered across services. Can you build something that assembles a patient's
> full picture in one view? The portal already has a records endpoint you can build on.
> Make it feel fast, some of the record pages are a bit sluggish today. I'll send the
> network capture our QA person grabbed off the current portal.
>
> WHAT THEY HANDED OVER
> API spec: `GET /patients/{id}/records` — auth required, but no check that the caller's
> token matches `{id}`; `{id}` is a sequential integer.
> QA capture `portal.har`: a logged-in patient (own id 1042) requests
> `/patients/1042/records` → 200, then requests `/patients/1043/records` → 200, returning
> another patient's labs.
> Query log for one patient-view assembly: `SELECT * FROM records WHERE encounter_id = ?`
> runs 37 times (one per encounter), plus a full-table scan on records search.
> Session config `auth.yaml`: `SESSION_TIMEOUT: never` — tokens issued at login don't
> expire.
> Page-load metric: assembled patient view p95 = 3.8s, almost all DB time.
>
> QUESTIONS TO DIG INTO
> In the HAR, change the patient ID in the URL — does the server stop you, or hand over
> the chart? How are patient IDs generated — could you guess the next valid one? Count the
> queries behind one patient view — does it hold up for a real chart with 50+ encounters?
> When a clinician walks away from a shared workstation, when does their session actually
> end?
>
> CURRENT PROBLEMS (STATED / KNOWN)
> Patients want their labs + visit summaries in one place. Some record pages are sluggish.
>
> THIS WEEK'S DELIVERABLE
> A knowledge-graph schema (patient→encounter→provider→record) + a small multi-agent
> retrieval prototype that assembles the patient view with an ownership/authorization check
> at the graph boundary + an IDOR finding writeup (repro from the HAR) and an N+1 note.
> Keep the KG to a seeded sample; the security finding is the headline. — note that
> 'multi-agent' ~= single agent if single agent is sufficient to achieve desired
> functionality. Currently no patient UI exists I believe.
