> 1. Every non-refused coverage answer must cite source title, section, and effective or version or retrieval date.
> 2. The assistant never invents coverage answers.
> 3. On conflicts or unclear applicability: cite both, refuse a definitive coverage answer, escalate.

**Problem scoping.** Today the assistant turn (`services/ai-assistant/app.py` `visit_chat`)
runs `understand → act → ground → phrase`: intent and the payer lookup are deterministic
and the model is consulted last, choosing action ids from a closed catalog. There is no
tool-use path (`llm_client` does structured output only), no policy-document corpus
(`eval/rag/` is the RIV-160 chart-record eval, a different corpus, and "preloaded" besides),
no agent framework dependency, and LangSmith wraps exactly one span
(`tracing.py` around `_BedrockMessages.create`). No correlation id crosses portal →
gateway → ai-assistant, and no live-Bedrock run has ever been recorded in the repo
(`docs/todo.md` TODO-9/TODO-10 open since W1). The ask is an extension of the existing
path — same boundaries, same controls — with the model-directed retrieval inserted before
the eligibility action and the single span grown into one trace.

The client package supplies what the ask assumed we would author: 87 approved documents
(`document-manifest.json`: 44 federal public-domain extracts, 14 payer + 2 X12 **citation-only**
records, 26 original synthetic clinic procedures/summaries), each carrying document id, title,
section labels, version/effective date, retrieval date, plan/product/state applicability,
allowed roles, license disposition and content sha256; six business policies (access matrix on
the shipped roles, answer boundary, verification/reverification, five-tier conflict resolution,
privacy/visibility, synthetic payer mix); and the acceptance harness — 32 evaluation cases
(`evaluations/eligibility-assistant-evaluations.jsonl`, 23 categories) plus seven isolated
negative fixtures (`FIX-NEG-*`) that must never enter the corpus. The package is explicitly not
a design; it fixes the corpus (eligibility-assistant-D-6 amended), the citation shape, and the pass/fail line.

**Corpus and harness, measured (E-3).** The 87 approved documents total **131 KB** (~1.5 KB
each, ~30K tokens), pre-sectioned markdown whose section labels, category, payer/publisher,
applicability and dates are already in the manifest — the "~700K / 114 files" figure was
the whole package (csv/json duplicates, policies, fixtures). Retrieval over this corpus is
a metadata lookup on the client's own precedence rule (payer → product → state → date, else
escalate), not semantic search (eligibility-assistant-D-13). Joining the harness against the manifest: 16 of
the 32 cases cite at least one source that is **not a manifest row** (`policies/*.md`,
`procedures/*.md` by path, `evaluations/fixtures/README.md`), and 5 cite only such sources —
so "cite only what was retrieved" and "one test per case" cannot both hold on the harness as
literally written; eligibility-assistant-D-12 fixes what each source kind asserts. The existing action catalog
(`visit_templates.py`) has eight ids and **no** refuse / escalate / conflict / care-first id;
`VisitIntent` has five values; the harness expects 26 distinct `expected_outcome` values —
eligibility-assistant-D-15 separates the outcome vocabulary from the action ids. Nothing in the request, facts,
or intent carries an emergency signal (eligibility-assistant-D-14), and no correlation id exists on any hop.

## Appendix — outcome vocabulary and harness mapping (eligibility-assistant-D-12, eligibility-assistant-D-15)

**Outcome enum (closed, ten values):** `active` · `inactive` · `unknown` · `unavailable` ·
`reverify` · `conflict` · `refuse_definitive` · `refuse` · `stop` · `care_first`. An outcome
is what the turn concluded; the action ids (REQ-4′) are what the reply does about it. Harness
qualifiers such as *-network-unknown* / *-auth-unknown* / *-with-boundary* are `active` plus a
required action id or boundary template, never a separate outcome.

**Source kinds in `expected_source_ids` (eligibility-assistant-D-12):** a manifest `DOC-*` id must be retrieved
on the turn and rendered as a citation; a `procedures/*.md` path is the manifest row it is
vendored as (`DOC-FRONT-DESK-SCRIPTS`, `DOC-COVERAGE-QUESTION-CHEAT-SHEET`, …) and is asserted
the same way; a `policies/*.md` path governs behaviour and is asserted as the outcome / action /
refusal the case expects, never as a citation; `evaluations/fixtures/README.md` is the corpus
gate. A `DOC-*` id expected on a **deterministic turn** is satisfied by the reason table below —
fetched by id through the same bounded index and rendered, so the assertion is the same on
both paths (eligibility-assistant-D-19).
