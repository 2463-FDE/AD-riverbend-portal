  1. A — Direction F as drawn. ui-serif, "Iowan Old Style", Palatino, Georgia on headings and the patient name, system sans everywhere else. The serif is F's argument: it marks the identity strip and page titles as document rather than instrument, which is why §3 rations it and keeps it out of queue rows.
  2. B — the serif removed, nothing else changed. One system UI stack throughout; headings survive on size and weight, tightened -.014em because SF/Segoe at 29px tracks looser than Palatino does. Cheapest possible answer to "how does it look without" — and the only set that removes a whole failure mode, since a heading and its body can no longer fall back to different families on an unusual workstation.
  3. C — grotesk. Colder and narrower; reads as instrument, not document — closest to what clinical software normally looks like, which is either the point or the objection. Widest install base here: Helvetica or Arial is present on every platform, so what a Windows desk sees is what a Mac sees.
  4. D — humanist. Keeps F's warmth without a serif. Open apertures hold up better than the grotesk at the 11px uppercase label step, which is the smallest type in the system. ⛔ Cost: this set resolves to a genuinely different face per platform (Avenir Next on macOS, Segoe UI Variable on Windows, Corbel behind it), so the render is not stable across workstations the way B and C are. Correction, 2026-08-01: this line originally said "the way A, B and C are", which was wrong about A. A leads with the ui-serif generic, whose mapping is per-browser and not inspectable, and names Palatino, which does not match Windows' Palatino Linotype — so a Windows workstation fell through to Georgia by accident, not by choice. A was never platform-stable; it only looked it. E is per-platform too (Charter on macOS, Cambria on Windows), but both outcomes are named, screen-drawn faces rather than one named face and one accident.
  5. E — serif kept, changed. Chosen 2026-08-01. The original argument on this line was that Charter and Cambria were drawn for screen text at small sizes — true, but largely spent, because §3 rations the serif to 18px and up and keeps it out of queue rows. The argument that survives is DPI, not size: Charter (Carter, 1987) was cut for 300dpi laser output, low stroke contrast and sturdy stems; Cambria was commissioned for ClearType and is among the most aggressively screen-hinted serifs shipped. Palatino and Iowan Old Style carry high thick/thin contrast whose thins fall below one pixel at 1x/96dpi and drop out or smear — so the gap widens on exactly the older clinic hardware this has to run on, and it does not close at 18px. Second reason, and the decider: this stack is more predictable than A (see below).
  6. Nothing here is decided — superseded. 05-design-tokens.md §3 now pins set E, amended 2026-08-01 with the reasoning and the measured font-availability evidence, and a new §6.5 recording the low-DPI margins that decided it. This page followed §3, as this line always said it would: the default set above is E. It still does not own the decision — if the set changes again, §3 changes first.

Riverbend Community Health · staff portal

Sign in

For Riverbend staff. Patients do not have accounts here.

Riverbend signs you out after 10 minutes without activity.

  1. The form posts to the portal's own server, never to the gateway. That server holds the gateway bearer token and returns a sealed session cookie — httpOnly, SameSite=Lax, no Max-Age, no Domain attribute (FE-R30). Secure is derived from the deployment's ORIGIN scheme, not hardcoded: hardcoded true on a non-localhost HTTP origin makes the browser discard the cookie silently and every later request arrives unauthenticated with no error to read.
  2. Nothing about the session is readable from JavaScript (FE-R27). Today's portal writes the token to localStorage — the pattern OWASP and SMART on FHIR both name specifically as the thing not to do.
  3. The logoff interval is stated on the login surface, before it can surprise anyone mid-form. 10 minutes, per ADR 0014 §4.
  4. No "forgot password", no "remember me", no self-registration. No such endpoint exists, and dead affordances teach operators the interface lies (wireframe plate 1 note 5).
  5. ⛔ No copy addresses the operator as a patient (FE-R13, FE-R24). Today's dashboard opens "Good day, Front" and offers "a summary of your care".

Sign-in is unavailable The portal could not reach the sign-in service. Nothing was changed. Try again in a moment; if it keeps failing, tell the help desk.
Reference c7f4-1e
  1. Two different failures, two different messages. A refused credential is the operator's to fix; an unreachable gateway is not, and telling them to "check the password" wastes the shift.
  2. Both branches arrive as HTTP 200. The gateway's _post/_get return r.json() regardless of downstream status, so a rejected login is 200 + {"detail": …} and a transport failure is 200 + {"error": str(e)}. FE-R2 names all three branches — non-2xx, detail body, error body — because the second was in the original wording and the third was not.
  3. ⛔ The upstream string is never rendered. str(e) can carry hostnames, connection strings and payload fragments; FE-R16 forbids PHI in an operator-facing error, and this is the cheapest place to leak it. The correlation reference is for the log, and the log line is what carries the detail.
  4. ⛔ No username enumeration. One message for a bad username and a bad password.
  5. The password field clears; the username survives. Cross-flow rule 6 — preserve operator input across failure — with the one exception every browser already expects.

Signed out after 10 minutes idle

any route → /login FE-R28driven at G2
Riverbend Community Health · staff portal
Signed out There was no activity for 10 minutes, so Riverbend ended the session on the server. Sign in again to carry on.
  1. The timeout is enforced server-side from last_seen inside the sealed cookie, a value the browser cannot forge. A client timer alone is a suggestion. ADR 0014 §4.
  2. The portal calls the existing POST /logout, which destroys the gateway's Redis session. A timer that only clears client state leaves a live, unexpiring credential behind — create_session sets no TTL.
  3. The redirect is not the proof. FE-R28's gate evidence is a request made after the timeout coming back 401; the CI half is unit tests on the timer and the staleness check, both pure functions. Same split as FE-R27 and half of FE-R29 — the harness has no server, no database and no network, so anything verified "after login" is driven at the gate and written down. G2's signature rests on that record.
  4. The reason is stated. A silent bounce to login reads as a bug and gets reported as one.
  5. Open, not decided: whether a warning precedes the logoff. ADR 0014 specifies none. A front-desk operator mid-registration losing ten minutes of typing is the argument for one; it is also new state and a new failure mode, so it is a decision, not an edit.
  6. ⛔ This does not close D10. The Redis session still has no TTL. A token captured before the timer fires stays valid forever, and only the gateway can fix that.

  1. Four consents, and every one of them is storable (FE-R21). That is what the P2 backend half buys: ConsentKind widens from three to five with financial_responsibility_ack and communications_opt_in. Today the form takes a financial attestation and the service discards it. The fifth member, roi_consent, is collected by no UI at all — which is why FE-R21's test is a subset assertion plus a pinned-literal enum, not set equality.
  2. Three consent states on screen, one in the data (FE-R11). The consents table has no status column — _record_consents inserts one row per accepted kind and nothing else — so "Declined" and "Not answered" are indistinguishable in storage by construction. Keeping them apart is a UI obligation the data cannot help with, and the copy above says exactly what is written rather than implying more. The chips derive from the §2 rule, unchanged: tint for a settled answer, dashed outline for one that never came, glyph on every chip so the column survives greyscale.
  3. SSN is type="text" (FE-R12). Today it is type="password", so the browser's password manager offers to save a patient's SSN into a workstation profile. autocomplete="off", and the field states its own posture — plaintext TEXT in Postgres, D3, unchanged by this rebuild.
  4. The policy-holder name is gone, replaced by the bit that is actually consumed. Measured, not assumed: the only consumer is policy_holder_is_self: !ins.policy_holder — a boolean derived from emptiness — and the name string reaches nothing but a review display. Collecting PHI-shaped free text that no column stores is worse than not collecting it. The checkbox's helper line is the honest half: unchecking it records the fact and loses the name.
  5. Typed date of birth, no picker. The native picker opens on the current year and reaching 1974 means dropdown hunting; FE-R7 owns the real fix at G3, and a text field with a stated format is the P2 floor, not the answer.
  6. Nothing here is written to localStorage, sessionStorage or IndexedDB (FE-R29). Draft-preservation across a refresh would be a patient record at rest on a shared clinic workstation.
  7. Not in P2, deliberately: search-first entry (FE-R6, G3), the duplicate-match step, per-section review with edit. Registration opening on a blank form is the RIV-160 duplicate generator, and it stays open until P4.

  1. This is the defect the whole rebuild is named after. On main today, intake-service returns 422, the gateway relays it as HTTP 200, and the portal prints "Intake submitted successfully" over a patient that does not exist. It shipped past npm run build and 730 passing tests because nothing asserted the two sides of the payload.
  2. ⛔ A 200 is not proof (cross-flow rule 2). The portal treats a detail body, an error body, or a missing patient_id as failure regardless of status.
  3. The failure names the patient and states what was not written. "Every write shows what it wrote" runs in both directions — an operator who cannot tell whether a record exists will either create a duplicate or skip a real registration.
  4. Every entered field survives, and "Review the entry" returns to the form populated (FE-R2, cross-flow rule 6). ⛔ Never a cleared form.
  5. The validation detail is not rendered. A 422 body echoes the submitted payload — names, dates of birth, member IDs — so printing it puts PHI on a waiting-room screen and into any screenshot of it (FE-R16).
  6. The three branches are not equally reachable, which the test fixture has to respect. The error branch is not produced by a slow payer — ELIGIBILITY_TIMEOUT_SECONDS is 8s inside _post's 30s httpx timeout, so ADR 0010 returns pending. It is reachable when intake-service is down or restarting. The fixture is "intake unreachable", not "payer slow".

A registration cannot be edited after this point — Riverbend has no update path today.

  1. The confirmation states what was created, not "success" (FE-R1, cross-flow rule 1): identity, patient_id, the MRN's absence, how many consents were recorded, and the eligibility result.
  2. No MRN is assigned at registration, so none is shown. Checked against the code, not assumed: _create_patient (services/intake-service/app.py:118) never sets mrn, the column is nullable, and the only MRN generator in the repo is db/seed/generate_seed.py:118 — seeded rows only, format M####. A patient registered through this screen has mrn = NULL, and IntakeResponse carries no MRN field to render even if one existed. Earlier drafts of this plate showed RB-0041782, which is both unbuildable and in a format nothing here produces. The row states the absence rather than dropping it, because a front-desk worker who expects an MRN needs to know it is not coming yet — and the banner is already the honest answer for how the chart is retrieved: found by name. Whether intake should mint an MRN is an open decision no FE-R covers; it is entangled with RIV-160, since an MRN issued per registration numbers the duplicates rather than preventing them. Canonical statement: flow 1 ✗f.
  3. The eligibility result is already in the response and currently thrown away (FE-R20). Surfacing it is a rendering change; moving the check off the request thread is D4's remaining half and is approval-gated — out of scope here.
  4. "Check eligibility again" re-reads; it does not record. The button is wired today — GET /eligibility?insurance_id= exists at services/gateway/app.py:214 — but the answer lands nowhere. _create_coverage (services/intake-service/app.py:143) constructs the insurance_coverages row without status or verified_at, and no code path anywhere updates either afterwards, so the row keeps its 'unknown' column default permanently — even when the payer answered active during this very registration. The re-check is therefore true only on the screen showing it: nothing downstream, and no later shift, can see that coverage was ever confirmed. Recorded as D4b in docs/debt-log.md; persisting the result is not in P2's scope and is not drawn here.
  5. ⛔ Unknown is never rendered as "not covered." ADR 0010 returns pending/unknown on payer trouble rather than a false inactive, precisely so a covered patient is not turned away at the desk. "Unknown" takes the solid attention chip because it is the state that needs a person; the copy says unconfirmed, not refused in words.
  6. Allergies read "not captured by the interface feed", not blank (FE-R5). HL7 AL1 segments are dropped upstream (D6), so silence and "none known" are different clinical facts and must never render alike.
  7. "2 of 4 accepted" must come from the response, not from the form. FE-R21 makes every collected consent storable; it does not make the count on this screen true. _record_consents (services/intake-service/app.py:158-167) commits one row per consent in its own transaction and swallows each failure — it logs and continues — and create_intake returns its 201 regardless. So a partial write is indistinguishable from a complete one, and a count rendered from submitted form state can claim a consent that never landed. That is the legacy portal's defect class exactly: reporting a success the client never confirmed. This plate therefore owes an additive IntakeResponse field echoing the consents actually committed, and the number here reads from it — FE-R33, added 2026-08-01, with flow 1 ✗g as the canonical statement. Seam-sized, no gateway edit, no ConsentKind change.
  8. Post-submit correction is honestly unavailable. No update endpoint exists, so no edit affordance is faked (flow 1 ✗d). This is the reviewed screen's sharpest operational objection — no edit path means the workaround for a transposed DOB is re-registration, which is the RIV-160 duplicate generator wearing a different hat. Naming it here does not fix it: a write path touches PHI columns under a mutable, non-tamper-evident audit log (D2) and is approval-gated (CLAUDE.md §6).
  9. The payload behind this screen is the shared fixture (FE-R3): tests/contracts/intake_payload.json, asserted by a pytest test and a JS test, sitting outside both frontends. It is what stops the two sides drifting again — and it is the enforcement for the dropped policy_holder key, which no FE-R covers by decision.

What these plates do not show

  • Everything behind G3 and later. Name-and-DOB search (FE-R6), the persistent identity banner (FE-R4), the four-step wizard with per-section review, role-aware navigation (FE-R14, behind G4 and an explicit auth approval), appointment and ROI queues with clinic-timezone rendering (FE-R8–R10).
  • Any change to the gateway. require_session is never asked to accept a cookie and no gateway file is edited — that invariant is the whole reason a server-held token is available at P2 instead of at G4.
  • The IDOR fix. Removing the numeric ID box is a read-path affordance, not an authorization change. Sequential patient IDs stay walkable until W4 binds a session to a patient.
  • A patient-facing surface. Blocked on that same session binding, not on frontend work.
  • Small-viewport behaviour. Unverified since P0.4 — Chrome would not resize below ~1500px during the walkthrough, so the narrow state has unknown status and nothing here is a mobile decision.
