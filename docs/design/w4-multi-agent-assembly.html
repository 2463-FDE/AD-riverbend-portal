Multi-Agent Patient-View Assembly

Proposed orchestration for the W4 ask — "assemble patient view." The agents earn the fan-out by routing and reducing, not by fetching in parallel: one probe call decides the shape, and the agent graph differs by volume (a 2-visit chart spawns fewer agents than a 60-visit one). Wrapped by the security gate W4 exists to fix — IDOR on /patients/{id}/records, plus the second cross-patient path through /records/search — and the N+1 chart read. Clinical interpretation of gaps sits behind a deferred W7/W8/W9 boundary, not built here. The fan-out is not the latency fix; bounded, indexed, batched reads are (see notes).

Where the speed actually comes from

The client ask says "make it feel fast." The fan-out does not do that — it adds hops. The latency win is entirely in bounded reads, and the writeup must attribute it that way with before/after query counts: batched encounter→record loading instead of 1+N (records-service/app.py:112 runs one query per encounter, deliberately); a patient_id-scoped, indexed search with a LIMIT instead of a full-table ILIKE (app.py:152); and a recency window + cap on high-volume charts. The agents earn their keep by deciding what not to fetch. Presenting parallelism as the performance story invites the obvious rebuttal — three agents on one service and one database is more work, not less.

Notes

Rev. 2026-07-27 — three corrections against the previous sketch, all found by reading records-service/app.py: (a) the demographics retriever was a bare PK read doing no reduction, so it collapsed into the orchestrator's probe — one call, not three; (b) the search agent called /records/search, which has no patient_id predicate, so a "patient view" was reading across all patients behind the authz gate — now scoped and bounded; (c) the raw service responses flowed straight to the assembler and the gap detector read the datastore directly, both bypassing the dedup and the volume bound — everything downstream now consumes the reduced set. Reviewer pass (2026-07-24) had already reshaped this from three parallel GETs into agents that route and reduce.

Open questions before it becomes an ADR (tracks docs/specs/w4.md §7): (1) does "session bind" mean patient-ownership or a care-relationship check — Riverbend has no such table yet; (2) is the fan-out worth it vs. one retriever — resolved: justified only by routing + reduction, else collapse to a single retriever; (3) semantic dedup of free-text notes can collapse clinically-distinct findings — prototype dedups structured fields only, with provenance, needs an adversarial test before any LLM merge; (4) HITL gates add latency — confirm which are mandatory vs. break-glass only; (5) where do the agents run — ai-assistant (8077, but that is the only vendor-egress path) vs. gateway-side (shorter hops, but the gateway is a load-bearing wall that owns auth); (6) does the probe need a new endpoint — no endpoint returns count/span today, and getting the count by fetching the whole chart defeats the probe. Additive only either way. IDOR/N+1 fixes touch the auth boundary → human approval required per CLAUDE.md §6 before any code lands. "Full picture in one view" is scoped to the viewer: full-for-a-clinician ≠ full-for-a-patient (D7 → W9).
