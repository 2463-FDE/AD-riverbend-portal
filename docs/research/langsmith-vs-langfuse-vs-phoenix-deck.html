04 · Cost, short term

One container vs a four-service stack

Phoenix · self-host

One stateless container

  • SQLite by default; Postgres for prod — reuse the one we run
  • Stateless → scale horizontally behind one Postgres
  • ~$0–15/mo compute; ~$0 riding existing Postgres
  • Fits a Docker-Compose shop with no new operational surface
Langfuse · self-host

Four services to run

  • ClickHouse + Postgres + Redis/Valkey + S3/MinIO
  • Prod floor: 4 CPU / 16 GB RAM / 100 GB disk
  • Four stateful services to run, monitor & patch — a cost independent of volume
  • A whole new datastore fleet to run, monitor & patch

The scale that stack unlocks is scale Riverbend does not have. A single clinical-summary feature is low-thousands of traces/day — well inside a one-container deployment.

Lowest ops is also lowest cost — and it's the compliant one.5 / 11

07 · Intellectual honesty

When LangSmith or Langfuse win

LangSmith wins when…

Turnkey & LangChain-deep

  • You're all-in on LangChain / LangGraph
  • You want hosted SaaS + vendor support + a contractual BAA
  • You can fund Enterprise for managed self-host
  • Default tier is a third-party PHI path — not us today
Langfuse wins when…

Server-side controls, out of box

  • Immutable audit logs, retention, server-side masking, project-RBAC — with the EE key
  • Broader platform: prompt management, cost analytics, annotation queues
  • More permissive MIT license than Phoenix's ELv2
  • Cost: the EE key + a four-service ClickHouse stack to run

Phoenix's own gaps, honestly: per-project RBAC, multi-tenancy, SSO/SAML, server-side ingestion masking & advanced security live in Arize AX, not the OSS build; auditor-grade audit logging in the free build is unverified — confirm before deployment; prompt & cost tooling is lighter than Langfuse. For Riverbend's single low-volume feature, footprint + OTel portability outweigh these.

Right tool per job — Phoenix is the fit for a regulated, small-footprint shop.8 / 11
08 · Widening the field

Alternatives beyond the three

OpenLLMetry / TraceloopInstrumentation only

Not a platform — an OTel SDK that only emits spans (one line, auto-instruments Anthropic/LangChain). No storage, no UI, no evals: you must pair it with a backend to see anything. The most barebones option — and Phoenix can be that backend.

HeliconeSelf-host · Apache-2.0

Proxy/gateway between app and provider; adds caching & cost controls. Self-hostable and permissively licensed — but the proxy model adds a hop in the request path.

Datadog LLM ObsSaaS · BAA

The pick if we already ran Datadog. BAA available on enterprise — but it's another vendor, another PHI contract, and another bill.

W&B WeaveSelf-host (heavy)

Eval-centric, OTel-ingest capable. Self-managed exists but is heavy — license + Kubernetes + ClickHouse + S3, the same weight as Langfuse. The SaaS path needs a BAA.

BraintrustHybrid · CI evals

Eval + CI-gating, generous free tier. Hybrid deploy keeps the data plane in your own cloud (Terraform AWS/GCP/Azure); control plane stays SaaS. Full HIPAA BAA is Enterprise-only.

The through-line

None displaces the core requirement: keep PHI-bearing traces inside a boundary we control. Phoenix meets it with the lightest footprint — and speaks the same OTel standard Traceloop defines.

Wider field, same constraint — self-host or bring a BAA.9 / 11

10 · The recommendation, in one paragraph

Rationale

recommended

For Riverbend's LLM tracing and evaluation we recommend Arize Phoenix, self-hosted next to the Postgres we already run. The gating factor is compliance posture: an observability tool stores the full prompt and completion, so it holds more PHI than the vector store — patient name, DOB, MRN, and clinical notes — and every store that touches that data must sit inside a business-associate relationship or a boundary we already control. Self-hosting keeps every trace in-network, so no vendor touches PHI and no BAA is required — and that BAA-free posture is shared by self-hosted Langfuse, making the BAA a wash between them and LangSmith the outlier, whose self-host and contractual BAA gate behind an Enterprise tier (~$100k/yr floor) while its default tier ships PHI to a third party. Between the two self-host options the discriminator is footprint and lock-in: Phoenix deploys as a single container reusing our Postgres, where Langfuse self-host means operating four stateful services — ClickHouse, Postgres, Redis, and an object store — regardless of volume. Phoenix is OpenTelemetry-native, so it auto-instruments our Anthropic/Bedrock calls with no lock-in and a cheap exit to any OTel backend, and it ships built-in hallucination evals aimed at our ungrounded-summary safety risk. In candor: on the server-side control set — audit, retention, server-side masking, project-RBAC — the free Phoenix build is thinner than EE Langfuse; source-side OpenInference redaction (backend-agnostic) plus our own network boundary close that gap, with free-build audit-log auditor-grade to confirm before deployment. Riverbend's trace volume is clinic-scale, comfortably inside Phoenix's single-node envelope — so the extra scale the others offer is capacity we would pay for and never use. Phoenix is the lowest-footprint and most portable option, and clears the same in-network compliance bar as any self-host — decisive for a small regulated shop with one low-volume feature.
