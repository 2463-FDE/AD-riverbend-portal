## 1. Client ask (verbatim)

Persona: Dr. Maya Okonkwo, COO, Riverbend Community Health.

> Patients keep calling to ask how to see their own labs and visit summaries — right now it's
> all scattered across services. Can you build something that assembles a patient's full picture
> in one view? The portal already has a records endpoint you can build on. Make it feel fast,
> some of the record pages are a bit sluggish today. I'll send the network capture our QA person
> grabbed off the current portal.

## 2. What it really is (decoded defect)

- **"records endpoint you can build on"** is the IDOR surface itself: `GET /patients/{id}/records`
  requires a session but never binds it to `{patient_id}`, and IDs are sequential/walkable. Building
  on it as-is **propagates the bug** (D11).
- **"sluggish record pages"** = N+1 / unindexed reads in the records read + search paths (D8).
  ⚠️ **The multi-agent fan-out is not the latency fix, and must not be presented as one.** Agents add
  hops. The speed comes entirely from *bounded* reads: batched encounter→record loading instead of
  1+N (`records-service/app.py:112`), a `patient_id`-scoped and indexed search with a `LIMIT` instead
  of a full-table `ILIKE` (`app.py:152`), and a recency window + cap on high-volume charts. The agents
  earn their keep by deciding **what not to fetch** — that decision is the D8 story; the parallelism is not.
- **"full picture in one view"** is a decoded phrase too: *full* is scoped to the viewer. Full-for-a-clinician
  ≠ full-for-a-patient (D7 minimum-necessary), so "full" here means "assembled across services," not
  "every field to every caller." Enforcement is W9 — see the deferred boundary in §3.
- The **network capture** (`docs/handover/portal.har`) is expected to reproduce the IDOR (one
  session reading a patient it does not own).

## 3. Scope

### In scope
- IDOR analysis of `GET /patients/{id}/records` (and sibling record reads) — how the missing
  ownership/care-relationship check lets a session walk sequential IDs.
- N+1 / full-scan analysis of the records read + search paths (D8).
- A **multi-agent retrieval prototype** that assembles a patient view — prototype quality, to
  demonstrate the assembly *shape*, not a production feature. Reviewer feedback (2026-07-24)
  resolved open-Q2: the fan-out only earns its keep if the agents **route and reduce**, not just
  GET in parallel. So the prototype must show agentic work beyond parallel fetch:
  - **Volume-aware orchestration, on one probe call.** Orchestrator probes *first*, then routes:
    few visits → fetch-all; 50+ → recency-window + rank-by-relevance + cap. Doubles as the D8
    bounded-read story (never full-scan a 50-visit chart to render one view).
    The probe is **one call** returning header demographics **plus** encounter count/span. A
    separate "demographics retriever" agent is explicitly **not** in scope: `GET /patients/{id}`
    (`records-service/app.py:72`) is a single primary-key read that reduces nothing, so a dedicated
    agent for it is exactly the parallel-GET fan-out open-Q2 rejected. Fold it into the probe.
  - **Conditional fan-out.** The number of retrievers is a **function of volume**, not a fixed
    three: the few-visit path spawns one bounded chart retriever and **no search agent at all**;
    the 50+ path additionally spawns a scoped relevance retriever to drive rank + cap. A prototype
    whose agent graph is identical for a 2-visit and a 60-visit patient has not demonstrated routing.
  - **Patient-scoped search.** Any relevance/search retrieval must be scoped to the target
    `patient_id` and bounded. Today `GET /records/search` (`records-service/app.py:137`) does an
    unbounded, unindexed `ILIKE` across **every patient's** records — inside a patient-view assembly
    that is a second D11 read path that Gate 1's `patient_id` bind does not cover, not merely a D8
    performance issue. `records.patient_id` already exists (`models.py:47`), so the scope predicate
    is available; the missing index and `LIMIT` are the D8 half.
  - **Reduction in retrievers.** Dedup records repeated across visits while keeping **provenance**
    (source-visit refs) — deterministic dedup on structured fields (lab code, dx code), **not**
    an LLM/semantic merge of free-text `notes` (see risk, §7.3). Reduced output is what downstream
    steps consume: the assembler and the gap detector read the **reduced** record set, never the
    raw service payload or the datastore directly (else the bound and the dedup are decorative).
  - **Deterministic coverage-gap detection.** Emit derived *facts* — last-observed date per
    category vs. expected cadence (e.g. `no CBC since 2023-01`). Facts only; clinical
    interpretation of those facts is out of scope (below).
- A **KG / patient-view schema** sketch (encounters · records) the assembly reads from.
- The **IDOR writeup** + HAR repro (primary deliverable).

### Explicitly OUT of scope (defer to the owning week)
> This is the section that keeps a "north-star" diagram from being mistaken for the W4 deliverable.
- **Clinical interpretation / patient-facing advisory language** — turning a gap fact into guidance
  like *"you haven't had bloodwork in 3 years, so your status on X may have changed"* is an ungrounded
  clinical claim. Detecting the gap as a **fact** is in scope (§3 above); *interpreting* it for a
  patient is **not** — it needs the D1 grounding guard (W7), redaction-before-vendor (D13/W8), the
  minimum-necessary patient-vs-clinician view (D7/W9), and a clinician HITL. Draw it as future, don't build.
- **D7 minimum-necessary / RBAC** → W9. Do not build role/scope enforcement here.
- **D1 LLM grounding guard** → W1 (shipped) / W7. Do not add a grounding gate as W4 scope.
- **D13 PHI-to-vendor / redaction-before-boundary** → W8.
- **D2 / D12 append-only audit trail + disclosure accounting** → W10 capstone.
- **HITL gates** (break-glass, clinician confirm) — not in any current spec; note as a future
  question, do not build.
- **D10 session TTL** — borderline (tagged W4/W9 in CLAUDE.md §9). Analyze/flag if it intersects
  the IDOR fix, but do not ship session-expiry behavior under this week without human approval.

### 3.1 Capability vocabulary — naming only, no enforcement (added 2026-08-02)

> **Why this is here and not in W9.** D11's fix binds a session to a `{patient_id}`. Three of the
> four reads below are cross-patient *by construction* — there is no single patient to bind them to
> — so the fix has to answer "which reads are legitimately cross-patient, and for whom." That is a
> capability question, and W4 cannot avoid answering it just because D7 owns roles. Answering it
> with a hard-coded list of exempt route paths is the version W9 would have to rewrite; naming the
> capability each read needs is the version W9 merely populates. This section is the naming. It
> ships **no** enforcement, no `roles.yaml` edit and no auth-behaviour change, so it sits outside
> CLAUDE.md §6's approval gate — and the moment any of it becomes a check in code, that gate applies.

| Read | Route | Capability it would require | `config/roles.yaml` today |
|---|---|---|---|
| Chart read | `GET /patients/{id}/records` | `records.read` **plus** the D11 patient bind | grants `records.read` to `staff` |
| Record search | `GET /records/search?q=` | `records.search` — cross-patient by construction; the D11 bind cannot express it | no such permission exists |
| Day queue | `GET /schedule?date=` | `schedule.read` — cross-patient by construction | **no appointment *read* permission exists at all**; the file has only `appointments.write` |
| ROI queue | `GET /roi/requests` (`patient_id` optional) | `disclosures.read`, and per-disclosure 164.508 authz (D12/W9) | grants `disclosures.read` to `staff` |

Three facts this rests on, each checked against the tree rather than assumed:

- **`config/roles.yaml` is read by no code.** Its only references are prose — `CLAUDE.md`,
  `ARCHITECTURE.md`, three ADRs, this spec set. It defines seven permissions and enforces zero, so
  today it is documentation that describes an intent no request path consults.
- **A principal is already available at the gateway.** Login stores `{"username", "role"}` in the
  session hash (`services/gateway/security.py:278`) and `require_session` returns it. A capability
  check therefore needs no new session state and no login change — it needs a policy to consult.
- **The enforcement surface is one file.** 18 routes carry `Depends(require_session)`, all in
  `services/gateway/app.py`. W9's blast radius is one dependency per route, and it grows by roughly
  one route per feature week — bounded and known, which is why deferring enforcement to W9 is cheap
  and deferring the *vocabulary* is not.

**What W4 must therefore produce (in deliverable #1, not as code):** for each cross-patient read,
the capability name and the sentence justifying why that read is legitimately cross-patient. W9's
RBAC spec consumes that list as its role→capability matrix input. What W4 must **not** produce: a
`require_capability` dependency, a `roles.yaml` edit, or a route-path exemption list.

## 4. Deliverables (artifacts that must exist for "Done")

1. `docs/…` IDOR writeup — the vuln, the HAR repro steps, the fix (bind session identity →
   `patient_id` via ownership or care-relationship check), and why the fix touches the auth boundary.
   Includes the §3.1 capability vocabulary: every cross-patient read named with the capability it
   would require, so the fix hangs on a capability rather than on a route-path exemption list.
2. Multi-agent retrieval **prototype** (code, clearly marked prototype).
3. KG / patient-view **schema sketch** (doc or `.sql` proposal — not a shipped migration unless approved).
4. D8 N+1 / full-scan finding (batched fetch + indexed search recommendation, with evidence).
5. ADR if a non-trivial design decision is made (per project rule: decisions get an ADR, not just code).

## 5. Acceptance criteria (done-definition — the diffable part)

- [ ] IDOR is **demonstrated**: a characterization test (or documented HAR repro) shows a session
      reading a patient it does not own **succeeds today** (matches the existing `xfail`).
- [ ] Proposed fix **binds session identity to `{patient_id}`**; writeup states whether the bind is
      patient-ownership or care-relationship, and names the missing table if one is required.
- [ ] **Every cross-patient read is named with the capability it would require** (§3.1), and the
      writeup states for each why it is legitimately cross-patient. A fix that instead exempts route
      paths from the patient bind fails this criterion — that is the shape W9 would have to rewrite.
      Naming only: no capability check, no `roles.yaml` edit ships under W4.
- [ ] D8: at least one read path shown to issue N+1 / full-scan queries, with a bounded/indexed
      alternative proposed (evidence, not assertion).
- [ ] Prototype assembles a patient view **through the gateway**, never calling a domain service
      directly (portal → gateway → service invariant, CLAUDE.md §1).
- [ ] Prototype demonstrates **agentic routing + reduction**, not just parallel fetch: the few-visit
      path and the 50+-visit path differ (window / rank / cap), and retrieval dedups with provenance.
- [ ] **Agent graph differs by volume.** The retriever set spawned for a low-volume patient is a
      strict subset of the high-volume one (no search/rank agent on the few-visit path). Show both
      traces side by side; identical graphs = routing not demonstrated.
- [ ] **Probe is one call**, returning header demographics + encounter count/span together. No
      standalone demographics-retriever agent exists in the prototype.
- [ ] **Search/relevance retrieval is scoped to the target `patient_id` and bounded** (`LIMIT` +
      supporting index proposed). An **adversarial test** asserts a scoped search cannot return a
      record belonging to another patient — this is a D11 path, so the negative-test rule applies
      (CLAUDE.md §5), not just a perf note.
- [ ] **Every service call in the prototype traverses the gateway** — no retriever holds a
      records-service URL. Stated explicitly in the writeup: where the agents run (ai-assistant 8077
      vs. gateway-side) and therefore what the hop chain is.
- [ ] **Assembler and gap detector consume the reduced set**, not raw service payloads and not the
      datastore directly. A path that reaches Postgres without passing Gate 1 and the volume bound
      is a finding, not a shortcut.
- [ ] The writeup attributes the latency improvement to **bounded/indexed/batched reads**, with
      before/after query counts — not to the fan-out (§2).
- [ ] Coverage-gap detection emits **facts only** (last-observed vs. cadence); no patient-facing
      clinical advisory language is generated under W4 (that belongs to W7/W8/W9).
- [ ] No out-of-scope debt (D7/D1/D13/D2/D12) is silently implemented; anything touched there is
      flagged, not shipped.
- [ ] Any auth-boundary change is **flagged for human approval** and NOT merged without it
      (CLAUDE.md §6). W4's shippable output is analysis + prototype; the live IDOR fix may land later.
- [ ] Adversarial / negative test for the authz check exists if any authz code is written
      (RIV / PR #2 negative-test rule, CLAUDE.md §5).

## 6. Relevant landmines (CLAUDE.md §6 / §9)

- ⚠️ **IDOR on chart reads** — `GET /patients/{id}/records` requires a session but never binds it to
  `{patient_id}`; IDs sequential + walkable. Intentional, documented-in-code gap. **Never change auth
  behavior without explicit human approval.**
- ⚠️ **N+1 / full-table scans** in records read/search paths (D8/D10 amplified · W4).
- ⚠️ **`GET /records/search` is a second cross-patient read path** (`records-service/app.py:137`):
  no `patient_id` predicate, no `LIMIT`, no index. Binding the session to `{patient_id}` on the chart
  endpoint does **not** close it — an assembly that calls search unscoped re-opens D11 behind Gate 1.
  Scope it before using it in any patient-view path.
- ⚠️ **PHI handling** — `notes`, `ssn` plaintext; do not widen exposure when assembling a "full view."
- ⚠️ **IDOR prevention is an `xfail`** in the suite (cross-patient reads currently succeed) — do not
  "fix" the test to hide the gap; characterize first.

## 7. Open questions (resolve before this becomes an ADR)

1. Does "session bind" mean patient-ownership or a care-relationship check? Riverbend has **no such
   table yet** — a care-relationship model may itself be a schema deliverable.
2. ~~Is the multi-agent fan-out worth it vs. a single retriever?~~ **Resolved (reviewer, 2026-07-24):**
   parallel fetch alone is not worth it. Fan-out is justified *only* by agentic **routing + reduction**
   (volume-aware retrieval, dedup with provenance, gap-fact derivation). The prototype must demonstrate
   that, or collapse to a single retriever and say so.
3. **Semantic-dedup risk (new):** merging free-text `notes` phrased differently across visits can
   collapse two *clinically distinct* findings into one. Prototype dedups **structured fields only**,
   with provenance; any LLM/embedding merge of narrative text is deferred and needs an adversarial test
   (RIV/PR #2 negative-test rule, §5) before it's trusted.
4. Which (if any) HITL gates are mandatory vs. break-glass-only? (Latency cost — likely defer to W9/W10.)
5. **Where do the agents run (new)?** Two options, and they imply different hop chains and different
   blast radii:
   (a) **ai-assistant (8077)** — matches "8077 is the LLM service," but it is also the only
       vendor-egress path (CLAUDE.md §2/§6), so a patient-view assembler living there puts assembled
       PHI next to the egress boundary and every retrieval becomes ai-assistant → gateway →
       records-service.
   (b) **gateway-side orchestration** — shorter hops and Gate 1 is right there, but the gateway is
       the standing example of a load-bearing wall (CLAUDE.md §10.3) and it owns auth; adding agent
       orchestration to it is not a seam.
   Unresolved. It is an auth-boundary-adjacent decision, so it needs a human call and probably the ADR.
6. **Does the probe need a new endpoint (new)?** The one-call probe (demographics + encounter
   count/span) has no endpoint today: `GET /patients/{id}` returns demographics with no counts, and
   getting the count currently means fetching the whole chart — which defeats the point of probing.
   Options: extend `PatientDetail` additively, or add `GET /patients/{id}/view/probe`. Additive-only
   either way (CLAUDE.md §7); a contract change gets flagged before it is written.
